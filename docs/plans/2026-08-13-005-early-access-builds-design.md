# Early Access Builds page + beta blog wiring - Design

- **Date:** 2026-08-13
- **Status:** Approved (brainstorm with maintainer, 2026-08-13)
- **Scope:** New unversioned "Community" docs section with an Early Access Builds page, plus resolving the page-dependent TODOs in the 2.0 beta blog post.

## Background

The upstream visual repo ([dm-p/powerbi-visuals-html-content](https://github.com/dm-p/powerbi-visuals-html-content)) now has Deneb-style release automation (upstream PR #189): channel pre-releases on rolling `alpha`/`beta` release tags, plus tagged production releases. The `alpha` tag is live (`2.0.0.alpha-1`) with two `.pbiviz` assets - one per edition. The `beta` tag is coming; the 2.0 beta testing push (draft blog post `blog/2026-08-03-2-0-0-beta.mdx`) will point at the beta channel.

Deneb's [Early Access Builds page](https://deneb-viz.github.io/community/early-access) is the structural model: intro / is-this-for-me / general information / providing feedback / per-channel access + installation + identification.

## Facts sourced from the live alpha release

These are load-bearing content inputs, verified against the `alpha` release on 2026-08-13:

- Each channel drop ships **two packages**: `HTML-Content.<version>.pbiviz` (full rendering) and `HTML-Content-Secure.<version>.pbiviz` (sanitized, external communication blocked, matching the certified AppSource visual's behavior).
- Channel builds use **channel-specific visual IDs** (`ALPHA`-prefixed for alpha), so they side-load alongside the AppSource visuals and each other without interfering, and do not auto-update.
- The channel Secure build is **not certified** and carries none of the certification benefits of the published AppSource visual.
- **The in-product version reads `2.0.0.0` for every channel build.** The package filename (e.g. `HTML-Content.2.0.0.alpha-1.pbiviz`) is the only way to identify a drop. Issue reports must quote it. *(Superseded 2026-08-14 by upstream PR #190: channel builds now stamp the fourth version segment with the commit date and short hash, e.g. `2.0.0.20260813#5f7ca17e`, shown in-product, plus an amber not-for-production badge on the landing page. Feedback quotes the filename and the in-visual version.)*
- Channel builds are not supported for production use.

## 1. Site structure

Changes to `docusaurus.config.ts`:

- Add a second `@docusaurus/plugin-content-docs` instance: `id: "community"`, `path: "community"`, `routeBasePath: "community"`, versioning disabled, autogenerated sidebar via a new `sidebarsCommunity.ts` (same autogenerated pattern as `sidebars.ts`).
- Add a **Community** navbar item linking to `/community/early-access`.
- New repo-root `community/` directory containing `early-access.mdx` (slug `/community/early-access`) - the only page for now. The `.mdx` extension is deliberate: the page carries MDX `{/* */}` comments, and markdown formatters (format-on-save) mangle those in `.md` files into invalid expressions that crash the page at runtime.

Link-integrity: as a docs-plugin instance, the community section is covered by the existing `onBrokenLinks: "throw"` gate.

### Dependency: production must include `/docs/next`

The page (and the blog post) deliberately point testers at the 2.0 working docs under `/docs/next`. This is already satisfied: the deploy workflow builds with `INCLUDE_NEXT=1` (`.github/workflows/deploy.yml`), so `/docs/next` is live in production. Consequence: `INCLUDE_NEXT=1 npm run build` becomes the canonical local build command - a plain build (1.6 only) fails by design once content linking into `/docs/next` lands, and AGENTS.md gets a note saying so. *(Superseded 2026-08-14: the version gate and `INCLUDE_NEXT` flag were removed entirely when 2.0 was opened in the version dropdown for beta - plain builds now include both versions.)*

## 2. Page content: `community/early-access.mdx`

Title: **Early Access Builds**. Voice per AGENTS.md (calm, developer-direct, hyphens not em-dashes). All new H2/H3 anchors pinned with explicit `{#id}`.

Outline:

1. **Intro** - AppSource publication/certification is slow and hard to roll back; catching issues before submission gets everyone a better release. Two channels: Alpha and Beta.
2. **Is this for me?** - expectations checklist: builds exist for giving feedback; not supported for production; documentation for in-flight features lives in the 2.0 working docs (`/docs/next`) and its change log; builds are decoupled from AppSource - not certified, no self-update.
3. **General information**:
   - Two packages per drop (table: package / edition / what it does), with the Secure-edition certification caveat.
   - Channel-specific visual IDs; side-loads alongside AppSource visuals; no auto-update.
   - **Identifying your build** - own pinned-anchor H3 (`{#identifying-your-build}`): in-product version reads `2.0.0.0` for all channel builds; quote the package filename.
   - Watch the GitHub repo for release notifications (link to GitHub's notification docs).
4. **Providing feedback** - pinned anchor; link to [GitHub issues](https://github.com/dm-p/powerbi-visuals-html-content/issues). What to include: package filename, steps to reproduce, expected vs actual (ideally vs 1.6 behavior), screenshots or short videos, anonymized sample content/measures or workbook. Warning admonition: test with copies of production reports, not originals.
5. **Alpha Channel** - Accessing the build ([`alpha` release tag](https://github.com/dm-p/powerbi-visuals-html-content/releases/tag/alpha), always the latest drop, both `.pbiviz` assets at the bottom of the release page); Installing (link to [Microsoft's import-a-visual-file docs](https://learn.microsoft.com/en-us/power-bi/developer/visuals/import-visual#import-a-visual-file-from-your-local-computer-into-power-bi)); Identification (icon and landing page - screenshot TODOs with descriptive alt text).
6. **Beta Channel** - same structure targeting the [`beta` release tag](https://github.com/dm-p/powerbi-visuals-html-content/releases/tag/beta). The section lands now with a note that the beta build is published when a release candidate is ready; screenshot TODOs.
